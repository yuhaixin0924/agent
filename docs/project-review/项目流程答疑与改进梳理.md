## 1. 当前架构

### 1.1 项目定位与层次

项目帮助用户寻找实习线索、核对岗位原文，并结合个人条件分析机会。`internship` 是英语“实习”，用于程序包和工具命名。

```text
入口 A：DSH 插件路径
用户对话
  → DSH 宿主：模型服务、对话、工具注册与调度
      ├─ 宿主中可用的搜索工具：执行搜索
      └─ 本项目 dsh-internship 插件
           → Node 接入层 src/index.js：注册工具、接收参数
           → Python bridge.py：校验请求、分发操作
           → candidates.py / agent_snapshot：候选、网页、证据、匹配
           → 插件 SQLite：保存网页快照、候选与证据卡
           → HTML 报告；client.js 提供 DSH 看板入口

入口 B：独立 CLI 路径（不经过 DSH）
用户输入 python -m internship_agent …
  → __main__.py：按命令安排流程
  → core.py / research.py：采集、规则匹配、模型评估
  → llm.py：直接调用配置的模型接口
  → 独立 SQLite、报告文件
  → mail.py：可选日报及人工确认投递
```

当前是**两个已有入口，各带业务实现和独立数据**，不是“一个后端、两个界面”。插件使用独立 Python 代码快照，不会自动调用根目录 CLI；独立程序不只是插件的邮件助手。两边的档案、岗位和邮件状态不会自动同步。

| 比较 | 独立 CLI | DSH 插件适配层 |
| --- | --- | --- |
| 输入者与形式 | 用户输入命令、参数和文件路径 | DSH 模型提交工具名和 JSON 参数 |
| 流程决策 | 命令的预设程序流程 | 模型选择下一步；插件执行与校验 |
| 模型接入 | 独立 `llm.py` | DSH 宿主的模型适配器 |
| 结果 | 终端、文件、可选邮件 | JSON 工具结果、对话解释、看板 |

“适配层”负责把入口协议转换成业务调用。CLI 已经存在，不需要再新增第三套终端程序；CLI 也不等于已经具备终端自然语言聊天。

### 1.2 DSH 的参与范围、模型与图片能力

DSH 是外部宿主，不是某一个大模型。本项目开发的是其中的实习插件。官方架构明确：模型适配器、工具注册、会话与 Agent 循环本身都是插件，可通过配置替换。[官方架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/HEAD/docs/architecture.md)

**多模型：当前官方文档支持。** 可在 Settings → Models 添加第三方服务或自定义接口，再选择模型；自定义服务支持的协议包括 Chat Completions、Responses 和 Anthropic Messages。实际可用性取决于安装版本、服务和模型，不代表任意模型都能完成相同任务。[模型配置文档](https://github.com/deepseek-ai/deepseek-harness/blob/HEAD/docs/user/guide/providers.md)

**图片：当前官方文档已经提供图片输入支持。** 在 Settings → Models 编辑模型，进入 Customized settings → Model options，在 Input types 启用 Image。pi-ai 模型对应 `input: [text, image]`，直接 DeepSeek 适配器对应 `inputModalities`。这只是声明能力，所选模型和接口必须真实支持图片；勾选不会把文本模型变成视觉模型。[图片输入说明](https://github.com/deepseek-ai/deepseek-harness/blob/HEAD/docs/user/guide/providers.md#image-input)

核实边界：本次查到的是官方当前分支文档，没有核实用户本机 DSH 版本，也没有确认首次支持图片的发布版本，因此不能保证旧安装直接具备同样能力。宿主能理解图片，也不等于实习插件已支持图片简历、PDF/Word 解析或档案保存。

建议本机验证：记录版本 → 配置真实支持图片的模型 → 在会话可用的图片附件入口提交一张无隐私、含明显文字或图形的测试图 → 询问图中内容 → 检查实际回答和错误信息。该验证独立于实习插件。

独立 CLI 目前只实现文本模型调用，通过 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL` 配置 Chat Completions 兼容服务；还需支持代码使用的工具调用、`tool_choice` 和消息格式。没有图片消息构造流程，也没有统一实现其他协议。

### 1.3 主流程：谁处理什么、有什么用

**独立 CLI**：

| 步骤 | 执行者 | 操作对象与动作 | 作用／结果 |
| --- | --- | --- | --- |
| 配置 | 用户、`init` | 创建并填写档案、来源及可选邮件配置 | 确定替谁分析、从哪里采集 |
| 采集／导入 | `collect`、`sync`、`import` | 读取 JSON、RSS/Atom、Greenhouse | 得到岗位文本，不是全网自主搜索 |
| 规范化与去重 | `normalize`、`Store.ingest` | 校验字段、按 URL 识别岗位、按内容识别版本 | 写入岗位库，识别重复和变化 |
| 规则或模型分析 | `match/ranked` 或 `research` | 对照档案粗筛，或分批分析原文 | 生成冲突、未知项、证据卡和建议 |
| 导出 | CLI、SQLite | 保存事件、最近报告和评估 JSON | 供复查；最近报告文件会覆盖 |
| 可选邮件 | 用户、`mail.py` | 日报或草稿、审核、确认投递 | 通知自己或本人确认后申请 |

本地保存贯穿流程，不是直到最后才入库。

**DSH 插件**：用户表达需求 → 模型理解、可追问 → 插件生成查询计划 → DSH 搜索工具找链接 → 插件接收 URL、读网页、存快照 → 模型分析并提交证据 → 插件校验存档 → 对话解释与候选看板。

`plan` 只登记查询，不执行搜索。候选是 URL 线索，证据卡是经整理和引用校验的具体岗位记录；读取候选不等于完成个人评估。插件不验证 DSH 是否真的执行了提交 URL 所对应的搜索。

### 1.5 macOS／Windows 用户如何开始

**路径一：先看界面，最少依赖。** 用浏览器打开[空看板预览](preview/candidates.html)。Windows 可在资源管理器双击，macOS 可在 Finder 打开。它展示真实渲染器生成的空报告，不搜索、不调用模型，也不是完整操作界面。

**路径二：体验独立 CLI。** 在仓库根目录操作。以下 Windows 用 `python`，macOS 通常替换为 `python3`：

```powershell
python -m internship_agent --help
python -m internship_agent init
```

手动编辑生成的 `internship_data/profile.json`。再配置 `sources.json` 并 `sync`，或用 `import` 导入真实岗位 JSON。仅填档案不会自动出现岗位。

```powershell
python -m internship_agent sync
python -m internship_agent report
# 配置模型后，才运行付费评估
python -m internship_agent report --ai
```

规则报告不需要模型。AI 模型配置写入本地根目录 `.env`，档案及岗位文本会发给提供商。可通过 `report --ai --profile "档案JSON路径"` 换本轮档案；它不同时切换数据库与邮件配置。README 写过备用档案限于数据目录，但当前代码没有强制该路径限制。

**路径三：在 DSH 使用插件。**

macOS：先装 DSH 和 Python，退出 DSH，在 `dsh-internship` 目录按[插件安装说明](../../dsh-internship/README.md)执行桌面运行时 CLI：

```bash
"/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh" plugin --profile desktop add "$PWD"
```

重启后先要求“调用 `internship_status`”，再检查档案、生成计划，最后测试真实岗位。

Windows：当前官方桌面文档有 Manage dsh Command 功能，可注册命令到用户 PATH；新开终端运行 `dsh --version` 确认。桌面安装和 npm CLI 的插件环境并非无条件相同，应核对正在使用的运行时与 profile。[官方桌面命令说明](https://github.com/deepseek-ai/deepseek-harness/blob/HEAD/apps/desktop/README.md#terminal-command)

本项目 Windows 接入仍有前置修复：插件默认 `python3` 本机未启动成功，需配置实际 Python 路径；`bridge.py` 读 schema 未指定 UTF-8，在默认 GBK 环境失败。Node 取消测试使用类 Unix 可执行脚本；冒烟脚本仍检查旧的 7 个工具而非 13 个。应修复并按本机 `dsh plugin --help` 核对安装命令后验收，本文不把 macOS 路径改写后当作已验证 Windows 安装方法。

插件档案可通过 `python -X utf8 python/bridge.py --data-dir "独立插件数据目录" --init-profile` 初始化，再手动编辑；在插件目录执行，macOS 通常用 `python3`。此命令不覆盖已有档案；数据目录必须与插件配置一致。插件默认是 `~/.dsh/internship/`。

### 1.6 从哪里开始测试效果

建议按“无模型 → 后端 → 宿主 → 真实样本”顺序：

| 层级 | 怎么测 | 能说明什么 |
| --- | --- | --- |
| 规则与流程 | 根目录 `python -B -m unittest discover -s tests -v` | 采集、匹配、证据卡校验和邮件状态的模拟测试 |
| 插件后端 | 插件目录 `python -X utf8 -B -m unittest discover -s tests -v` | 快照、候选、引用与复检；UTF-8 参数只用于本次测试进程 |
| Node 桥接 | 插件目录 `node --test tests/plugin.test.mjs` | 工具注册、子进程和取消；当前 Windows 有已知失败 |
| 宿主连通 | DSH 中 status → profile → plan → 读一条真实链接 → report/view | 插件是否加载、结果能否返回和显示 |
| 实际效果 | 人工核对少量真实岗位，检查引用、适用对象、城市和招聘状态 | 模型分析和规则在现实中的质量 |

此前结果：独立 Python 21/21 通过；插件 Python 默认编码加载失败，UTF-8 后 26/26 通过；Node 2/4 通过。本次仅重组文档，未重跑测试。没有实测真实模型、SMTP 或 Windows DSH 完整流程。

测试报告应区分“代码测试通过”和“真实推荐有效”。没有登录、JavaScript 渲染或 PDF 阅读能力的网页，可能无法读取；失败要展示原因。

### 1.7 当前与建议架构的边界

后续建议：以 DSH 为主要产品入口，逐步把两份核心抽成共同依赖包；保留已有 CLI 的明确功能，不新增第三套程序。

```text
DSH 适配层 ──┐
             ├→ 统一业务核心：档案／岗位／证据／匹配／评估
已有 CLI ────┘      → 由入口传入对应用户的存储对象
```

共用代码不等于混用数据库。近期可每人独立目录、SQLite、附件和邮件配置；这只是本地隔离约定，不是多用户认证。未来服务化需登录、授权、每次访问检查归属，不能信任模型给出的用户 ID。公开岗位可考虑共享，档案、评估、收藏和申请记录要隔离。

当前插件主动拒绝原 CLI 默认数据目录和带 `mail.env` 的目录，不能改路径强行合库。两份核心已有行为差异，要先统一规则、协议和回归测试，再抽取代码；独立分发插件还需打包共同依赖。

多个兼容插件可在 DSH 中并存，由模型协调调用；这不自动解决字段、身份、数据或固定业务流程整合。其他生态扩展是否兼容需核实协议。无需为了组合能力就复制合并所有插件源码。

## 2. 原理分析

### 2.1 技术与模块对应

| 模块 | 技术／文件 | 作用 |
| --- | --- | --- |
| 独立命令入口 | Python `argparse`；`__main__.py` | 命令解析与流程编排 |
| 采集和匹配 | 标准库 HTTP、XML、JSON、正则；`core.py` | JSON／RSS／Greenhouse、字段校验、规则匹配 |
| 模型评估 | Chat Completions 工具调用；`llm.py`、`research.py` | 结构化提交证据卡，格式及引用失败后修正 |
| 插件接入 | Node ESM、Cordis 工具注册；`src/index.js` | 注册 13 个工具，限制超时与输出 |
| 跨语言桥接 | `spawn` 子进程，标准输入输出 JSON；`bridge.py` | 不经 shell 执行后端；每调用一个进程 |
| 参数校验 | `schemas.json` 与 Python 校验器 | 类型、必填字段、长度、数量和允许值检查 |
| 持久化 | SQLite、JSON、SHA-256 | 岗位、版本、候选、快照、证据与事件 |
| 网页读取 | `HTMLParser`、TLS、公网地址校验、robots | 抽取公开网页文本；检查地址和重定向并固定已验证 IP |
| 看板 | Python 生成 HTML/CSS/JS；`client.js` 借宿主 React 展示 iframe | 本地筛选和 DSH 入口；不是独立前端应用 |
| 邮件 | `smtplib`、`EmailMessage`；`mail.py` | SMTP、附件快照、草稿审核及发送状态 |

网页安全读取是插件快照 `web.py` 的能力，不应套用成独立 RSS 采集器也有完全相同边界。插件候选队列有来源白名单，通用 `read_page` 主要按公开 HTTPS 网络边界检查。

### 2.2 个人档案字段

| 字段组 | 字段 | 含义 |
| --- | --- | --- |
| 基本情况 | `stage`、`background` | 年级／阶段、经历背景 |
| 能力 | `skills_known`、`skills_learning` | 已掌握与正在学习，不能互相替代 |
| 方向 | `cities`、`keywords`、`growth_goal` | 城市、搜索方向、成长目标 |
| 时间 | `days_per_week`、`months` | 每周可到岗天数、可持续月份，`null` 表示未知 |
| 取舍 | `priorities`、`hard_constraints` | 关注项与明确不可妥协条件 |
| 学历辅助 | `accepted_degree_labels` | 规则核对用学历标签，不代表招聘方确认资格 |
| CLI 额外字段 | `available_period` | 开始／结束日期和文字偏好；不表示已有完整日期推理 |

插件当前档案校验不接收 `available_period`，两边 JSON 不能保证原样互换。插件硬约束允许 `days_per_week`、`months`、`city`；独立核心对城市和默认硬约束处理不同。特别是独立程序在缺少 `hard_constraints` 时默认出勤／时长为硬约束，插件核心默认空。应显式填写字段，并在共享核心重构时统一。

可用的最小档案例子：

```json
{
  "stage": "大二",
  "skills_known": ["Python"],
  "skills_learning": ["Agent 开发"],
  "cities": ["广州"],
  "keywords": ["后端", "Agent"],
  "days_per_week": 3,
  "months": 2,
  "hard_constraints": ["days_per_week"],
  "priorities": ["learning", "attendance", "pay"]
}
```

未知不是零；档案示例只是格式，实际应由本人填写确认。CLI 和插件现在都没有从简历自动生成已确认档案的流程。

### 2.3 岗位、证据和版本字段

| 对象 | 主要字段／规则 |
| --- | --- |
| 岗位输入 | `title`、`company`、`url`、`description`、`city`、`degree`、`deadline`、`min_days`、`min_months` |
| 岗位规范 | 标题和正文不可为空，URL 为有效 HTTP(S)，结构化截止日期为 `YYYY-MM-DD`；出勤／月份未知可空 |
| 岗位身份和版本 | URL 的 SHA-256 摘要生成 ID；规范化内容哈希生成版本；记录首次与最近采集时间 |
| 独立证据卡 | `id`、`dimensions`、`questions`、`next_step`；每维 `fact`、`quote`、`interpretation`；附来源、岗位及档案版本 |
| 插件证据卡请求 | 主页面 ID、标题、公司、1～16 条 evidence、analysis、unknowns、next_step、reason |
| 插件单条证据 | `dimension`、`fact`、`quote`、`page_id`；保存时补来源 URL 与抓取时间 |
| 网页快照 | 页面 ID、地址、标题、正文、抓取时间；已读片段单独记录 |

独立按 URL 去重不是跨平台语义合并。插件候选额外规范化 URL、去追踪参数、保留岗位参数，并根据最终 URL 或全文哈希识别重复。

### 2.4 11 个分析维度

| 键 | 输出关注点 |
| --- | --- |
| `work` | 实际工作与任务 |
| `eligibility` | 年级与学历资格 |
| `period` | 起止时间、寒暑假、最短时长 |
| `attendance` | 每周出勤 |
| `remote` | 远程与地点限制 |
| `intensity` | 工作强度、单双休 |
| `learning` | 具体任务、培养资源 |
| `conversion` | 转正条件 |
| `skills` | 技术要求及可补足差距 |
| `pay` | 薪资、币种、计薪周期 |
| `benefits` | 保险、住房／餐饮补贴及适用对象 |

独立 AI 评估要求全部 11 维；缺事实则事实和引用留空、标未知。插件记录逐条证据，不要求同样的 11 维完整卡片，另允许 `company_context` 保存公司背景，未覆盖维度另列。公司通用信息不能直接当作实习生待遇。

住宿和通勤尚非独立维度；目前的房补字段不能替代住宿可行性分析。`priorities` 可影响独立报告维度展示顺序，但不是已经实现了加权综合评分。

### 2.5 固定输入与固定批次

独立评估本轮使用固定的档案快照和本地岗位池，不在分析中自行搜索补证；下次输入可以不同。固定还包括输出结构，不代表分析文字固定。个性化取决于档案质量及对取舍的理解，不由“固定”本身保证。

每批最多 5 条，默认最多 6 批；12 条按 5＋5＋2 顺序处理。正常 3 次模型请求，每批失败可修正一次；30 条最多 12 次请求。超过默认 30 条报错，不静默漏评。没有额外跨批次综合排名步骤；后批最终失败会抛错，尚无完整的部分报告与恢复机制。

规则报告有简单排序；AI 证据卡有问题和下一步，但没有专门的综合推荐榜。看板排序是筛查状态与来源，不是个人适合度。

### 2.6 引用校验能保证什么，不能保证什么

独立检查引用是否是对应岗位正文中至少 4 个字符的连续文字，并检查结构；插件还要求引用位于已经实际读过的页面片段。快照分页每次返回最多 10,000 字符，并保存已读范围。

**引用存在只证明文字来源，不证明结论成立。** 校验尚不能自动证明“适用于该岗位和人群”“足以支持概括”“招聘承诺会兑现”。

| 有原文依据的句子 | 不应直接推出 |
| --- | --- |
| 熟悉 Agent 开发者优先 | 实际工作一定包含 Agent 开发，而且有培养安排 |
| 员工享受住房补贴 | 实习生一定有房补 |
| 弹性工作时间 | 支持远程 |
| 本科及以上 | 接受大二学生 |
| 有转正机会 | 转正稳定或概率高 |

当前页面分类使用标题、URL 和正文关键词；城市判断使用字符串与上下文线索；时效使用截止日期、失效词和近期读取记录。攻略可能像岗位，注册地址可能被误作工作地点，可访问页面也可能已经招满。插件“疑似在招”要求近期成功读取等信号，时间窗口为 7 天，不是招聘方确认。

已有来源 URL、抓取时间和快照可供复查，HTML 候选链接可点击；来源可能是第三方，不能一律标官网。尚无完整逐维定位原文和快照对照界面。改进应增加语义复核、用户质疑后补证与人工标注验收，而不取消原文校验。

### 2.7 存储、隐私和邮件边界

独立默认 `internship_data/`；插件默认 `~/.dsh/internship/`。SQLite 保存事件和业务状态，报告文件导出最近结果；档案、简历、配置和密钥不应提交仓库。模型评估会发送相关档案和岗位内容，搜索也会向服务提交查询。

CLI `--profile` 不提供多用户隔离。每次入口应显式绑定用户上下文和存储对象，避免核心读取全局私人目录。共享核心建议统一 Profile、Job、Evidence、Assessment 等结构和版本，而非强行共用一个数据库。

CLI `draft --resume` 只接收不超过 10 MB、有 PDF 文件头的附件并保存快照，不解析内容。邮件经审核、当前版本确认后发送，记录 sending／sent／uncertain 等状态；不确定不盲目重发。`schedule-template` 只生成 macOS 配置，不安装、不启动。

目前 DSH 岗位到邮件没有接通：插件无草稿／发送工具，岗位也不自动导入 CLI。可手动转换岗位 JSON → import → draft → review → 终端确认 send。候选报告不能保证原样导入。

### 3.3 待讨论：用户提出的改进想法

| 想法 | 建议方案 | 需讨论的决定 |
| --- | --- | --- |
| 不先填资料也能咨询 | 每轮问一两项，允许跳过；从任务经历探索兴趣，生成方向假设和档案草稿 | 最少问到哪些信息才开始搜索；如何确认保存 |
| 简历／图片导入 | 文件选取 → 文字提取或 OCR → 模型提取草稿与依据 → 追问缺失项 → 确认入档 | 使用宿主能力、独立解析器还是组合；哪些原文保留 |
| 加住宿与通勤 | 区分宿舍、房补、适用人群、办公地点和个人预算；成本估算注明区间 | 是否独立第 12 维；哪些字段属于硬约束 |
| 综合推荐 | 先给优先了解／补证后判断／不优先，附冲突、理由和关键未知；再按偏好排序 | 是否需要数字分数；如何分开匹配和证据充分程度 |
| 用户质疑能更新 | 区分个人事实变化、偏好变化、证据错误、招聘状态变化，分别补证或重算 | 更新粒度、版本历史与跨岗位重排范围 |
| 点击依据看原文 | 每项提供来源、时间、快照；区分官网和第三方 | 是否做逐句高亮定位；如何展示历史与当前不同 |
| 多入口复用 | 抽核心包，入口传入用户存储对象，保留现有 CLI | CLI 长期范围、打包升级方式；是否共享同一人的数据 |
| 其他插件组合 | DSH 模型协调搜索、简历等兼容工具，必要时约定协议 | 接哪些插件、字段和身份如何传递；不假定跨生态通用 |
| DSH 选岗后申请 | 自动准备草稿及附件，用户核对当前版本后发送 | 岗位交接协议、真正用户确认入口、邮件权限与去重 |

反馈例子：

- “我现在每周能去四天”：确认后更新档案，不修改招聘事实。
- “学习比薪资重要”：修改偏好和推荐顺序，不改证据。
- “这只是全职员工福利”：重新核对适用人群，必要时撤回结论并标未知。
- “岗位已经下线”：复检并保存结果；读取失败记未知。

咨询引导建议按“阶段目标 → 做过的事情 → 喜欢的任务 → 时间地点成本 → 两三个方向假设 → 用户确认 → 真实岗位验证”推进。兴趣不等于职业定论，可提供小型体验任务帮助探索。

### 3.4 建议实施顺序

1. **P0：修基础。** 修正文档与命令差异、Windows 编码和 Python 路径、Node 平台测试与过期冒烟数量；确定演示环境。
2. **P1：做短闭环。** 咨询／简历草稿 → 用户确认档案 → 少量真实岗位 → 决策摘要与出处 → 用户质疑后修正。
3. **P1～P2：增强决策。** 加入住宿通勤、偏好比较、反馈版本和受影响项重评。
4. **P2：整理工程。** 逐步抽共享核心、设计岗位邮件交接、保存批次进度与恢复。
5. **持续：验证质量。** 人工标注员工福利套用实习生、任职偏好误作培养承诺、攻略误作岗位等案例；提供个人数据导出删除。

优先区分“现实上能不能去”和“可能获得什么”；先做能解释的推荐，不急着输出精确分数或扩大大量来源。自动准备申请与用户确认发送可以衔接，无须先合并两个数据库。

## 4. 演示汇报

### 4.1 展示方式

推荐“6～8 页简洁讲解稿＋真实候选看板＋短现场操作”。准备 60～90 秒真实录屏备用，替代现场失败部分，不重复播放同一完整流程。不必先做完整宣传视频。

也可用本地演示网页承载架构图、步骤和真实界面，但应优先保证真实操作跑通。空看板仅用于看布局，正式演示应使用少量已核对、标注采集时间的真实岗位和脱敏档案。

### 4.2 15 分钟安排

若包含问答，讲解控制在 12 分钟：

| 时间 | 内容 |
| --- | --- |
| 0～1 分钟 | 一个具体求职困境 |
| 1～3 分钟 | 产品定位与结果预览 |
| 3～7 分钟 | 一个完整、短的操作演示 |
| 7～9 分钟 | DSH／插件／Python 分工和证据校验原理 |
| 9～11 分钟 | 已实现成果、测试和局限 |
| 11～12 分钟 | 后续计划 |
| 12～15 分钟 | 问答与缓冲 |

### 4.3 建议演示内容

用一名大二用户、两三个真实岗位贯穿：已有档案 → 查询与候选 → 现场读一条岗位 → 展示到岗冲突和原文 → 打开来源／看板 → 对“熟悉 Agent 优先是否意味着能做 Agent”提出质疑并核对依据。

目前未实现的自动入档、完整反馈闭环和 DSH 邮件，不作为现成功能展示。可在后续方案页说明。全网搜索可提前完成，现场集中展示一条可靠读取和证据链；录屏标注等待剪短或使用历史结果。Windows 宿主未验收时，使用已验证环境录屏配本地报告，明确区分录屏与现场。

演示主线：**我们开发了运行在 DSH 中的实习证据工具，让岗位分析有来源可查、有未知项可见。**
