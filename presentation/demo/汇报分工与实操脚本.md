## 三、贯穿全场的主线（暂定）

> 同一个岗位，对不同的人可能意味着不同的机会。我们把个人条件、岗位原文与分析放在一起，让用户能追问推荐依据。

暂定主题：**让推荐有依据，让用户能追问。**（这句话可以放在标题下面，来体现效果）

模型是否识别冲突、是否调整结论，要用实际排练结果验证；不要预先编造排名或纠正成功的画面。

## 四、引入：我的内容（1 分 30 秒）

构思顺序：**具体情景 → 遇到的困难 → 开发动机 → 希望实现的功能**。先完成内容，之后再统一做视觉设计。

### 第 1 页：找到岗位之后，才开始真正的选择

暂定情景：一名想找 Python／Agent 方向实习的学生，在多个招聘页面间切换。他每周只能到岗两天，看到一个标题很合适的岗位，却还要核对出勤、实际工作内容和技能要求。

画面构想：只显示一位学生的需求与几个待回答的问题。第二位学生留到功能实操，避免开场就解释完整对照实验。

（这一部分可以以气泡框的形式讲述 “我” 面临的一些问题，后续美化的时候可以尝试我们再填补渲染几个虚拟的人物，一些小卡通形象等等都可以）
（第一张幻灯片是正经的极客的标题（项目名称），第二张幻灯片才开始进行引入）


参考讲稿（约 40 秒）：

> 想象一下，我们想找一份 Python 或 Agent 方向的实习，打开了几个招聘页面。岗位标题看起来都相关，但点进去才发现，有的要求每周到岗五天，有的只是把 Agent 写在优先条件里，实际工作是什么还不清楚。找到岗位之后，我们仍然要把这些信息和自己的情况逐一对照。

### 第 2 页：因此，我们想让实习分析更贴近个人，也更有依据

希望实现的功能对应前面的困难：

| 遇到的困难 | 产品目标 | 后面的展示如何回应 |
| --- | --- | --- |
| 同一个岗位不一定适合不同的人 | 结合个人档案分析条件 | A/B 档案对比 |
| 岗位信息分散，需要逐项核对 | 整理岗位事实、来源与未知项 | 展示原文引用和来源 |
| 看见推荐，却不清楚为什么 | 支持追问依据、重新核对 | 用户质疑后的解释 |

参考讲稿（约 35 秒）：

> 这让我们想到：能不能把个人条件和岗位信息放到同一个分析流程里？它既能指出哪些条件需要注意，也能保留原文依据；当我们不理解某个判断时，还能继续问“为什么”。带着这个目标，我们开发了 DSH 中的实习插件。

“希望实现”用于说明开发目标；“当前已经做到”要由后面的实际结果支撑。开场不承诺完整自动推荐、简历解析、反馈学习或自动投递。

交给朋友：

> 我们把这套流程做成了 DSH 中的实习插件。先由我的同伴说明宿主、模型和插件怎样配合，再回到实际操作。

## 六、功能介绍与实操：我的内容（6 分钟）

### 6.1 演示顺序

| 时间 | 操作 | 观众应看到什么 |
| --- | --- | --- |
| 0:00–0:45 | 确认已加载档案，快速展示候选与来源 | 从个人条件到岗位分析的流程 |
| 0:45–2:15 | 用档案 A 分析一条真实岗位 | 出勤条件、引用、冲突与未知 |
| 2:15–3:45 | 用档案 B 分析同一岗位 | 个人条件改变，分析随之变化；招聘事实不变 |
| 3:45–5:15 | 提出具体质疑，核对原文上下文 | 模型解释依据，必要时调整结论 |
| 5:15–6:00 | 展示来源／实际候选看板，回顾结果 | 哪些有依据，哪些还需要招聘方确认 |

准备两三条真实岗位，现场主要展开一条。A/B 尽量使用相同岗位和相同问题，减少搜索结果变化的影响。这是功能演示，不是严格量化评测。

### 6.2 三份演示档案

`profiles/` 中均为虚构教学资料，不代表真实用户；此轮没有改动实际 DSH 配置或个人档案。

| 档案 | 条件 | 作用 |
| --- | --- | --- |
| A | 大三；Python／SQL／Git；广州；每周 2 天、持续 6 个月 | 主演示：出勤受限 |
| B | 与 A 相同，主要差异是每周 5 天 | 主对照：观察出勤改变的影响 |
| C | 相同方向，但出勤与持续月数未知 | 备用：观察是否追问或保留未知 |

需要选取**原文明示出勤要求**的真实岗位。若页面没有写出勤，应该展示未知，不能为制造反差编造条件。不提前断定 B 一定值得推荐，因为其他要求仍可能不满足。

### 6.3 档案怎样进入当前插件

当前 `internship_profile` 读取插件配置的数据目录中的 `profile.json`；不能自动上传几份简历就创建多个用户，也不能通过这个工具直接修改档案。

排练前确定演示机器与实际 `dataDir`，使用独立演示数据目录。把选定的虚构档案放成演示目录的 `profile.json`，让插件配置指向该目录；是否需要重载，以实际 DSH 环境为准。

为了复用相同岗位证据，可在同一独立演示目录里依次替换虚构档案，每次调用 `internship_profile` 确认切换成功。不要覆盖私人档案。这只是单机切换方案，不代表多用户管理已实现。

A/B 各开新对话，先读取当前档案，再分析相同岗位。新对话减少旧上下文干扰，但不会隔离共用的数据目录。

### 6.4 操作提示词

**先确认状态与档案：**

> 请调用 internship_status 和 internship_profile，列出当前城市、每周出勤、持续月数、已掌握技能和正在学习的技能。缺失条件标为未知。先不要搜索或投递。

**完整流程快速带过／提前准备候选时使用：**

> 结合当前档案生成查询计划，使用你已有的搜索工具寻找具体岗位详情页，再交给实习插件记录与检查。分别说明候选数量和读取成功数量，不把关键词命中当作综合匹配度。

**现场主分析（替换为真实 URL）：**

> 请用实习插件读取并保存这条岗位的原文证据：〈真实岗位链接〉。结合当前档案分析主要工作、技能差距、城市、出勤和时长。分开列出原文事实及引用、结合档案的分析、未知条件和应问招聘方的问题。必要时重新取得当前档案与完整岗位信息。不要承诺录取，也不要投递。

**切换档案 B 并验证后：**

> 请对同一岗位依据当前档案重新分析，指出哪些判断因出勤条件改变而变化。招聘事实不变，不把旧分析直接当作当前结论。其他缺失条件继续保留未知。

### 6.5 质疑与核对：根据真实输出选择

若把“优先技能”推成“实际职责”，且原文确有类似表述：

> 你说这适合学习 Agent 开发，但引用写的是“熟悉 Agent 开发者优先”。这能证明实际工作会做 Agent 吗？请区分任职要求和工作职责，读取上下文核对；证据不足时调整表述，并列出应问招聘方的问题。

若把缺失信息当成满足：

> 你关于远程／转正／住宿的判断，具体依据是哪一句？请给原文和来源。没有明确说明就标为未知，不根据公司规模或行业习惯补全。

若结果本来就正确：

> 这项条件为什么影响当前档案？请展示原文要求和我的对应条件，解释判断过程。

展示目标是**能追问并核对**。模型可以修正，也可以依据证据维持原结论，不必刻意诱导它先犯错。

当前 DSH 可继续对话，并调用插件工具重读页面或快照；但尚无专门的反馈学习、偏好自动保存与持久化重排流程。若新结论只在对话中产生，不能说数据库已经自动更新。

### 6.6 结果在哪里看

- DSH：档案、分析、引用、未知条件与质疑后的解释。
- 原页面：引用上下文、来源和实际招聘状态。
- 插件候选看板：队列、来源、读取状态与待核对项；不是综合推荐排行榜。

原样稿 3030 中的空看板只用于布局预览。正式实操使用实际生成的报告，并标明获取时间。

## 八、收尾：我的内容（1 分钟）

暂定标题：**让推荐有依据，让用户能追问。**

收尾只做三件事：回扣开场问题、总结本次展示的价值、致谢。朋友刚讲完局限，不再逐条重复，也不需要再加一段完整展望。

参考讲稿（约 25～35 秒；根据实际演示结果调整）：

> 回到开头：找到一个岗位之后，我们还需要判断它是否适合自己。我们的尝试，是把个人条件、岗位原文和分析依据连在一起，让用户既能看结果，也能追问为什么。这就是我们开发这个实习插件的出发点。以上是我们的汇报，谢谢各位。

最后一页可以保留主题、项目名称与“谢谢各位”，仓库链接小字放在下方。若有答辩环节，可口头补一句“欢迎提问”；是否加这句以汇报流程为准。预留的 1 分钟是上限，不必为了用满时间拉长总结。

不要重复整套架构，也不要临时新增自动投递等未演示能力。
