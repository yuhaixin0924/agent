# 从实习 Agent 到 DSH 插件：我的开发记录

这是一份根据项目讨论、已有代码和实验记录整理的初稿。它记录了我这段时间踩过的坑、做出的选择，以及那些还没完全想明白的地方。我会随着真实使用继续修改它。

---

### 1. 最初的问题：我想找到适合自己的实习

我是一名计算机专业的大二学生，正摸索着寻找和 Agent 开发、后端及自动化相关的实习。对于第一次找实习的我来说，岗位的技术栈并不是唯一的考量：什么时候可以入职、每周得去几天、能否远程、团队能不能带新人，同样决定了这事儿能不能成、值不值得去。

一开始，我的想法很简单：写个 Agent 帮我满网搜实习，再结合我的简历给点建议。但用起来才发现，光拿到一堆链接根本不够——搜索结果常常带点“薛定谔的过时”，招聘网页上也总是缺这少那，而大模型又有个毛病，特别喜欢把自己的推测当成既定事实。

于是，我的目标慢慢变了：**不再追求“全自动帮你找工作”，而是帮求职者挑出值得进一步了解的机会，并老老实实说清楚依据是什么、哪些地方还拿不准。**

---

### 2. 为什么不只用关键词匹配？

最开始，我用的是笨办法：根据“Python”“Agent”“广州”这种关键词去过滤岗位。但很快发现，关键词只能告诉你“这个词出现过”，却根本回答不了“这个岗位每天到底干嘛”、“大二让不让去”、“只在寒假实习行不行”。

更重要的是，作为一个初学者，我可能还不会岗位要求的某项工具。如果仅仅因为一个关键词没匹配上就直接一刀切，我大概率会错过那些可以通过突击学习争取的机会。

所以，项目里我把关键词保留下来当个线索和简单统计工具，但让模型去结合岗位原文解释职责、要求和技术差距。至于时间、地点这些硬条件，必须由用户自己去确认；原文没写的，千万别瞎编，老老实实留白成“未知”。

不过这也带来一个局限：**模型能帮你梳理文字，却不保证解释正确。** 它说“这个岗位能学到很多”，并不等于导师真的有时间带你。

---

### 3. 为什么要保存原文和证据？

我最怕的就是大模型“热情地帮我脑补”。比如招聘页面写着“工作时间灵活”，模型一高兴就推导成“可以远程”；或者没写招几年级，直接脑补“接受大二”。

为了治治它的这个毛病，我加了网页快照和证据校验：

* 抓取网页时顺手把当时的整篇正文存下来，以后回看时有迹可循。
* 保存证据卡时，强制检查引用内容是不是已经读到的“连续原文”。
* 遇到没依据的盲区，宁可放进待确认项，也绝不凭空捏造。

开发时我还吃过一个苦头：一次提交多条证据时，只要其中一条引用不匹配，整次保存直接报错，而且报错信息含糊不清，模型只能像瞎子一样猜着重试。后来我改成：精确返回具体是哪条、哪个维度出了问题，并限制了连续失败的消耗。

当然，引用校验也只能证明文字在原文出现过，证明不了模型有没有断章取义。岗位是不是还在招、福利是不是对实习生有效，最后还是得靠人工去核对。

---

### 4. 为什么从独立 Agent 转向 DSH 插件？

项目早期，我搞的是一个独立的 Python Agent：自己写工具调用循环、自己维护用户档案、自己读网页、自己展示结果。我一度特别痴迷于让模型“完全自主”：让它自己决定下一步去搜索、阅读、补证据，或者在信息不足时主动停下。

但随着功能越来越多，我开始犯嘀咕：既然成熟的平台已经提供了现成的对话、工具调度和会话管理，我有必要从头到尾再造一遍轮子吗？比起把精力耗在这些通用基础设施上，我其实更想把时间花在求职场景的打磨上。

体验过 `dsh-ai-jobs` 之后，我看到了另一种分工的可能：用代码去批量整理岗位索引，然后按需分析，而不是让模型一条条去死磕枚举和整理。那次体验让我明白，工具调用次数多并不等于覆盖率高。不过话说回来，那个插件主要面向海外招聘看板，没法直接解决我关注的国内实习问题，它的索引量也不能和逐条深度分析的岗位直接划等号。

权衡之下，我决定把已有能力接入 DSH，而不是继续闭门造车搞独立 Agent：

> DSH（负责对话、模型调度、搜索）
> ↓
> 插件（负责岗位候选、个人档案、快照、证据校验、规则匹配）
> ↓
> DSH（根据工具结果向用户解释）

这个选择并不是说 DSH 一定比自建框架更牛，而是让我学会了**优先复用现成能力，把宝贵的注意力留给真正的需求本身**。

---

### 5. 为什么还要做 Python Bridge？

我原有的业务逻辑全是用 Python 写的，但 DSH 的插件入口偏偏是 JavaScript。如果把这堆代码全用 JS 翻译一遍，不仅费时费力，还极其容易引入各种奇奇怪怪的 Bug。

最后我折中搞了个“桥接”方案：DSH 调插件工具，JS 入口收到后转头去跑 Python 程序，把请求塞给它，拿回结果后再吐给 DSH。插件里保留了原来 Agent 的核心快照、存储和证据校验逻辑，但没有在工具内部再嵌套跑什么复杂的 `discover()` 模型循环。

这样既保住了之前的代码资产，又避免了“套娃式”地让一个 Agent 去调用另一个隐藏 Agent、导致流程黑箱化。当然，代价也是有的：两边的代码不会自动同步，后面得琢磨怎么优雅地维护这套共同的业务逻辑。

---

### 6. 为什么还要做候选队列和看板？

早期的插件只擅长“拿着现成的链接做分析”，但我的日常需求还包括“帮我发现新机会”。于是，我加了搜索计划、候选入队、链接去重、网页检查、报告和可视化看板。

这里有个挺容易绕晕的地方：**搜索计划不等于搜索结果。** 插件可以帮我生成查询词，但实际发起搜索还得靠 DSH 的搜索工具；插件收到 URL 之后，才把它当作候选线索。而且，候选也不等于有效岗位，点进去可能是一篇求职攻略、一个汇总页，或者早就 404 的过期页面。

我做看板的原因也很纯粹：在黑乎乎的对话框里看一长串让人眼花的 JSON 实在太反人类了。有一个直观的看板，我能一眼看出各个来源抓了多少候选、哪几个读取失败了、哪些需要人工复核，而不是只能对着聊天记录抓瞎。

在某次固定查询的早期测试里，8 次搜索拿到了 28 个去重候选 URL，实际检查了 10 个页面（8 个成功，2 个失败）；按当时的规则，居然没有一个页面同时满足四类证据信号。这个结果挺真实也挺残酷：它说明这套流程确实能跑出线索，但也赤裸裸地暴露了攻略页、主页、总公告和正文缺失带来的麻烦。它代表不了所有来源，也绝对不等于以后的每次搜索都能一帆风顺。

---

### 7. 为什么“在招”必须说得谨慎？

开发时我踩过一个大坑：网页复检失败的时候，系统顺手把“复检时间”给刷新了。结果好嘛，一堆早就失效的旧岗位因为更新了时间，在看板里被标成了“疑似在招”。要是真根据这个去改简历投递，非得白白浪费精力不可。

后来我把“尝试读取”和“成功读取”的时间戳彻底拆开了，并把状态重新划了三个档：

* **疑似在招：** 近期成功读取过，且页面结构和关键词符合详情页规则。
* **已失效：** 抓到了明确的过期信息、过了截止日期，或者直接返回 404/410。
* **状态未知：** 读网页翻车了、信息给得不够，或者老数据里缺乏靠谱的成功记录。

说到底，“疑似在招”也只是代码在那儿瞎猜，根本不能打包票说 HR 正在收简历。详情页识别、日期提取、城市匹配这些全都是死规则，难免会有误判，必须拿真实样本去一遍遍校准。

---

### 8. 哪些功能暂时不做？

在做这个项目的时候，我脑子里也蹦出过不少宏伟蓝图：自动生成日报、分析公司财务财报、搜股价、甚至直接帮用户一键代投简历。

但冷静下来想想，我现在最缺的不是花哨的功能，而是**怎么稳稳当当地帮我找到真实、靠谱、值得核对的岗位**。

所以，现阶段坚决不做自动投递、自动发邮件和定时日报。万一以后真要做投递，也必须加上一条死规矩：发送前必须由我本人亲自过目把关。至于个人档案，目前也只能老老实实手动维护，不给模型通过工具静默修改的权限。

我也琢磨过要不要给 DSH 写个专门的 Skill，让它按一套标准的求职流程来用现有的工具。目前插件虽然有了工具和说明，但还没独立的求职 Skill。这可以当作后续优化的方向，但绝对不能为了追求“功能多”而盲目增加系统的复杂度。

---

### 9. 现在有什么，还缺什么？

目前的版本已经搭得七七八八了：档案读取、候选发现与整理、网页快照、证据卡、规则初筛，再加上一个看得过去的看板。我已经成功在 DSH 里把整个插件跑通了——这证明打通这条链路没问题，但离“国内岗位覆盖全、匹配准确”还差得远呢。

接下来真正该去验证、也更有价值的事情其实是这几个：

1. 抓一批真实的岗位页面和非岗位页面（比如攻略、资讯），找真人手动标注一下，然后测测咱们的详情页识别、时效判断到底准不准。
2. 看看不同信息来源的实际“含金量”和可读性，挑出真正有用的源头重点维护。
3. 观察根据画像生成的搜索词，是不是真的能帮到不同背景的同学，而不是只适合我这个特定的城市和方向。
4. 盯紧真实的报错，用数据说话来决定接下来是加个 Skill、扩充来源适配器，还是引入更复杂的记忆机制，而不是为了炫技去堆砌功能。

折腾到最后，我希望这个项目带给我的收获，不仅是一个能帮我找实习的小工具，更是我对工具调用、数据边界、模型局限以及“人机协作”这件事儿有了一点真正属于自己的理解。
